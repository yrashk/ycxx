# Building ycxx

ycxx is built by GCC 16.2 (`-freflection -fcontracts`) against libycxx, the submodule at
`deps/libycxx`, with `import std;` (DECISIONS §3.1, §3.3). You need CMake 3.30 or later, Ninja
and Python 3.10 or later. Linux x86_64 and macOS arm64 are supported.

```sh
tools/build                      # configures build/ on first use, builds, runs the smoke test
build/bin/ycxx --version
tools/test --fast                # what the PR tier of CI runs (DECISIONS §9.1)
```

`tools/build` and `tools/test` first run `tools/sync-submodules`, which moves each submodule to
the commit this checkout pins. `git pull` does not, and a stale `deps/libycxx` builds against
the wrong library. A submodule with local changes at another commit (libycxx work in progress)
stops them instead, unless `YCXX_SUBMODULE_DRIFT=allow`.

## The compiler

`CMakeLists.txt` uses libycxx's toolchain file (`deps/libycxx/cmake/ycxx-toolchain.cmake`). It
finds GCC 16 in this order:
1. the compiler recorded in libycxx's toolchain cache (`~/.local/share/ycxx/toolchains`, or
   `$YCXX_TOOLCHAINS`);
2. `g++-16` or a `g++` reporting 16.x on `PATH`;
3. Homebrew's `gcc`.

If none is found, provision one with libycxx's script, which builds GCC from source into the
cache:

```sh
deps/libycxx/tools/toolchain/provision --gcc-only            # or --use-brew on macOS
```

Configuring with `-DYCXX_PROVISION=ON` does the same from CMake. GCC is the only bootstrap
compiler. Clang 23 is a black-box oracle (DECISIONS §2.3). It is never used to build ycxx and is
provisioned on its own: `deps/libycxx/tools/toolchain/provision --clang-only`.

## Layout

| Path | What |
| --- | --- |
| `src/main.cpp`, `src/driver/` | the one `ycxx` binary and its command line: `ycxx <front>` picks the daemon or a client (DECISIONS §4.7) |
| `src/daemon/` | the resident daemon (stub) |
| `src/client/` | the clients: `cxx` (c++-compatible, runs the pipeline in-process), `lsp`, `ctl` (stubs) |
| `src/pipeline/` | `ycxx.pipeline`: one translation unit from source to object, and the link to an executable (#43) |
| `src/hash/` | `ycxx.hash`: the 128-bit fingerprint (MurmurHash3_x64_128, fixed seed) and reflection-derived structural hashing |
| `src/engine/` | `ycxx.engine`: the query engine's core (docs/design/query-engine.md) |
| `src/ir/` | `ycxx.ir`: L1; `ycxx.ir.l2`: L2; `ycxx.ir.lower`: L1 to L2 |
| `src/interp/` | `ycxx.interp`: the L1 interpreter, for constant evaluation and whole programs |
| `src/target/aarch64/` | `ycxx.target.aarch64`: the AArch64 target description (forms, `aarch64.patterns`, calling convention), selection, stack-slot allocation, emission |
| `src/lex/` | `ycxx.lex`: translation phases 1–3, 5 and 6, the token kinds and literal values; Unicode tables generated by `tools/unicode/gen-tables` |
| `src/pp/` | `ycxx.pp`: the `pp` query and its region (directives not yet supported) |
| `src/items/` | `ycxx.items`: the item splitter, skeletons and item ids |
| `src/obj/` | `ycxx.obj`: the in-memory object file; `ycxx.obj.macho`: the Mach-O object writer and reader |
| `src/link/` | `ycxx.link`: the linker (signed arm64 macOS executables), driven by `ycxx cxx` |
| `tests/bootstrap/` | the bootstrap smoke test: one program per C++26 feature ycxx relies on |
| `tests/unit/` | unit tests, one CTest program per area (`ycxxc_unit_test`), run by `tools/build` |
| `tools/check-policy`, `tools/check-preprocessor` | stage-1 policy checks |
| `tools/build` | configure, build and run the smoke test |
| `tools/test` | the test driver (#5) |

CMake target names are `ycxxc*` and our options are `YCXXC_*`, because libycxx owns `ycxx*` and
`YCXX_*`.

## Preprocessor policy

libycxx's policy (`deps/libycxx/DECISIONS.md` §1) applies to ycxx in a stricter form, because
ycxx's sources are modules with no project headers. Only two directives are allowed: `#embed`,
and `#include <...>` of a system header inside a global module fragment. Configuration reaches
the code as values, such as the configured module `ycxx.version`, never as macros.
`tools/check-preprocessor` enforces this.

## Release builds

`tools/build` builds Debug unless told otherwise. A Release build (`-O3 -DNDEBUG`, still
`-Werror`) goes in its own directory:

```sh
YCXX_BUILD_TYPE=Release YCXX_BUILD_DIR=build-release tools/build
YCXX_BUILD_TYPE=Release YCXX_BUILD_DIR=build-release tools/test --fast
```

`YCXX_BUILD_TYPE` is read only when the directory is first configured, so use a separate
`YCXX_BUILD_DIR` rather than switching `build/`. `tools/test` tests `bin/ycxx` in
`YCXX_BUILD_DIR`, and its build stage runs `tools/build` with the same environment.
- `-DNDEBUG` does not turn contracts off: GCC's evaluation semantic stays `enforce`, so every
  `pre`, `post` and `contract_assert` is still checked. ycxx itself uses no `assert`.
- GCC warns differently with optimization, and has crashed only with it (#283). The places where
  ycxx's sources work around that are marked `// BOOTSTRAP:` and listed in STATUS.
- CI builds Release on Linux in the PR tier (compile only), and builds and tests it on both hosts
  in the nightly tier (`nightly.yml`'s `release` job, or dispatched alone with `release-only`).

## Optimizer experiments

Build the pinned HiGHS, CaDiCaL, and Chuffed sources in a separate build tree. This
project uses CMake, Ninja, Make for CaDiCaL, and a C/C++ toolchain. The first build
needs network access to GitHub's source archives. The archive hashes are checked at
download. Installation stays inside the build tree.

```sh
cmake -S cmake/solver-deps -B build-solver-deps -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=gcc-16 -DCMAKE_CXX_COMPILER=g++-16
cmake --build build-solver-deps --parallel 1
```

The independent targets are `highs`, `cadical`, and `chuffed`. Each installs under
`build-solver-deps/install/<solver>`. Set `-DYCXX_SOLVER_JOBS=N` to control the
parallelism inside each dependency build. For an installed libycxx toolchain, use a
fresh build directory and pass `-DCMAKE_TOOLCHAIN_FILE=<prefix>/lib/cmake/libycxx/toolchain.cmake`
in place of the explicit compiler arguments. The normal compiler build has no solver
download or link step. These experimental builds precede the pinned submodule
integration for in-process backends described in [DECISIONS §7](../DECISIONS.md#7-third-party-libraries).

CaDiCaL's source recipe includes the POSIX clock header explicitly for the Linux
libycxx build.

To check the compiler-owned model and run its generated FlatZinc through Chuffed:

```sh
cmake -S . -B build-optimizer -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DYCXXC_FLATZINC_SOLVER="$PWD/build-solver-deps/install/chuffed/bin/fzn-chuffed"
cmake --build build-optimizer --target unit_cm ycxx-cm-export-bench
ctest --test-dir build-optimizer -R '^unit\.cm' --output-on-failure
build-optimizer/tests/unit/cm/ycxx-cm-export-bench
build-optimizer/tests/unit/cm/ycxx-cm-export-bench --ndjson
```

The export benchmark builds its models before timing. Its three inputs isolate
serialization as the number of covering decisions grows.
[Benchmark module and runner](../packages/ycxx-bench/GUIDE.md).

Reproduce the extraction comparison from the e-graph spike with the same seed-derived
cases and limits. The repeated configurations reverse the order of the two blocks.

```sh
cmake --build build-solver-deps --target egraph-spike
build-solver-deps/egraph-spike demo
VERBOSE=1 build-solver-deps/egraph-spike random 10 30 300
NO_PRUNE=1 VERBOSE=1 build-solver-deps/egraph-spike random 10 30 300
NO_PRUNE=1 VERBOSE=1 build-solver-deps/egraph-spike random 10 30 300
VERBOSE=1 build-solver-deps/egraph-spike random 10 30 300
```
The optimizer design specifies how these experiments relate to corpus measurements.

## Sanitizer builds

`-DYCXXC_SANITIZE=<list>` (`address`, `undefined`, `thread`, comma-separated) instruments ycxx's
targets, the std modules and libycxx itself. `tools/tsan [-j N] [--repeat N]` is the
ThreadSanitizer build: it configures `build-tsan` with `YCXXC_SANITIZE=thread`, runs the unit and
daemon tests, then repeats the concurrent ones. Any report fails the test; a false positive gets
an entry with its reason in `tests/tsan.supp`. It needs Linux (GCC has no ThreadSanitizer on macOS
arm64), a GCC built with its sanitizer runtimes
(`deps/libycxx/tools/toolchain/provision --with-sanitizers`) and `vm.mmap_rnd_bits` at most 28.
The nightly `linux-x86_64-tsan` job runs on bare Ubuntu 26.04 (#105). Its glibc includes the
upstream loader fixes needed by the freestanding dynamic executable tests. The job logs its
glibc version and uses it in the GCC sanitizer cache key.
[#1377](https://github.com/yrashk/ycxx/issues/1377) ·
[Link-map fix](https://github.com/bminor/glibc/commit/8f8dd904c4a2207699bb666f30acceb5209c8d3f) ·
[Libc-free relocation fix](https://github.com/bminor/glibc/commit/706209867f1ba89c458033408d419e92d8055f58)

## Bootstrap smoke test

`tests/bootstrap/` compiles and runs small uses of the features DECISIONS §3.2 relies on, so that
a gap in the bootstrap compiler shows up on day one:
- modules with `import std;`;
- reflection: member-wise hashing, enumerator names, `define_aggregate`;
- contracts, including the violation handler;
- coroutines;
- `std::execution`;
- deducing `this`, pack indexing, structured-binding packs, constexpr exceptions,
  `std::expected` and `#embed`.

A feature the toolchain cannot compile yet is an expected failure. It has an `_xfail_<feature>`
entry with its reason in `tests/bootstrap/CMakeLists.txt` and an entry in STATUS. The entry's
test passes while the build fails, so a fixed toolchain shows up as a failing test.

## CI

`.github/workflows/ci.yml` is the PR and `main` tier, and `nightly.yml` is the nightly tier
(DECISIONS §9). Both run on Linux x86_64 (the `gcc:16` container) and macOS arm64 (Homebrew's
GCC). Each job runs `tools/check-policy`, then `tools/build`, then `tools/test` for its tier.
- A newer push cancels the older run.
- Changes to Markdown, `docs/` or `LICENSE` alone run nothing.
- A PR's first failing host cancels the other host.
- Toolchains come from libycxx's `tools/toolchain/provision`: `--gcc-only` on the PR and `main`
  tiers, both compilers nightly. Its prefix (`~/.local/share/ycxx/toolchains`) is cached. ycxx
  has no provisioning logic of its own.
- The nightly run skips itself when `main` has not changed since the last successful run.
- The last job of every run records its wall time with `tools/ci/wall-time`: the job summary,
  plus a `wall-time` artifact with each job and step. It warns when the tier is over budget
  (PR 15 minutes, main 60, nightly 240).
- A clean build takes about 20 seconds at `-j4`, so build outputs are not cached yet.
