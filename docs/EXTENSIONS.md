# Extensions

DECISIONS §1.2: ycxx accepts an extension only because a system header or libycxx needs it. Each
one is listed here with the headers that need it and what ycxx does with it. Nothing is added for
its own sake.

| Extension | Needed by | What ycxx does | Since |
| --- | --- | --- | --- |
| GNU attributes `__attribute__((…))`, before a declaration, among its decl-specifiers, and after a declarator | the macOS SDK's `<stdio.h>` family (`__printflike`, `__deprecated_msg`, `__swift_nonisolated_unsafe`), `sys/cdefs.h` | Parses the syntax and skips unrecognized attributes ([dcl.attr.grammar]/6) | #133 |
| GNU `[[gnu::visibility("hidden")]]` and `__attribute__((visibility("hidden")))`, including the `__gnu__` and `__visibility__` spellings | libycxx's `include/ycxx/core/new.hpp` and `src/runtime/linkage/static.cpp` | On x86-64 Linux, explicit hidden visibility on a declaration of an ordinary external namespace-scope function or non-inline variable gives its ELF symbol hidden visibility. ## The GNU dialect (`__GNUC__`)

ycxx predefines `__GNUC__` 4, `__GNUC_MINOR__` 2 and `__GNUC_PATCHLEVEL__` 1, as Clang does,
alongside `__ycxx__` (DECISIONS §1.5, #229). It does not define `__GNUG__`, `__clang__` or
`__llvm__`. libycxx recognizes ycxx by `__ycxx__` before it looks at `__GNUC__`, so no GCC path
of libycxx's applies to ycxx. The macOS SDK's headers then take their `__GNUC__` paths; what those
use, in the headers libycxx's C library headers reach (`<cstdio>`, `<cstdlib>`, `<cmath>`, …):

| Extension | Needed by | What ycxx does | Since |
| --- | --- | --- | --- |
| `__builtin_va_list`, a type name | `arm/_types.h`'s `__darwin_va_list`, ycxx's resource `<stdarg.h>` (including glibc's partial request), libycxx's `<cstdarg>` | `char*` in Apple's arm64 ABI and an array of one compiler-owned `__va_list_tag` in the System V AMD64 psABI (`ast::Target::va_list`). A declaration of the same name hides the builtin typedef-name in its scope. | #229, #383 |
| `__builtin_c23_va_start`, `__builtin_va_start`, `__builtin_va_arg`, `__builtin_va_copy`, `__builtin_va_end` | ycxx's resource `<stdarg.h>`, libycxx's `<cstdarg>` | The C23 spelling takes a cursor; the legacy spelling takes a cursor and a second expression whose value is unused. `__builtin_va_arg` reads a type-id. All five names answer 1 to `__has_builtin` on every target. The native definition and extraction subset is recorded in STATUS. | #196, #647, #676 |
| GNU attributes `__always_inline__` (`__header_always_inline`), `__format__(__strfmon__, …)` and `__format__(__strftime__, …)` (`__strfmonlike`, `__strftimelike`) | `sys/cdefs.h`, `_types.h`, `math.h` | Parsed and ignored, as the other GNU attributes (above) | #133 |
| `__builtin_fabsf`, `__builtin_fabs`, `__builtin_fabsl`, `__builtin_inff`, `__builtin_inf`, `__builtin_infl` | `math.h`'s inline `__inline_isfinite*`, `__inline_isinf*`, `__inline_isnormal*` (its `__GNUC__` and `__FINITE_MATH_ONLY__ == 0` path) and libycxx's `include/ycxx/core/cmath_builtins.hpp` | `__builtin_fabs*(x)` converts `x` to the type indicated by the suffix (`float`, `double`, `long double`) and clears its sign bit, including for NaNs. `__builtin_inf*()` is a positive infinity constant. On Linux x86-64, a dependent `__builtin_fabsl(x)` keeps its `long double` result type in template definitions and a concrete call diagnoses the unsupported x87 operation. `__has_builtin` reports the `long double` forms where ycxx supports the target's value format. A declaration of the same name hides the builtin (`lex::builtin_functions`). | #336, #201 |
| `__builtin_huge_val`, `__builtin_huge_valf`, `__builtin_huge_vall`, `__builtin_nanf`, `__builtin_nan`, `__builtin_nanl` | `math.h`'s `HUGE_VAL`, `HUGE_VALF`, `HUGE_VALL`, `NAN` | `__builtin_huge_val*()` is positive infinity. `__builtin_nan*("s")` takes a string literal and returns a quiet NaN whose significand below the quiet bit is `s` read as `strtoull` reads it (decimal, `0` octal, `0x` hexadecimal, empty for 0). `__has_builtin` reports the `long double` forms where ycxx supports the target's value format. | #336, #201 |
| `__builtin_addressof(x)` | libycxx's `<ycxx/core/move.hpp>` (`std::addressof`, [specialized.addressof]) | Uses ycxx's built-in address operation on an lvalue, preserving the operand type and bypassing `operator&`. Bit-fields and rvalues are ill-formed. Ordinary address-of limitations apply, including static member function names accessed through an object expression. The result can be a constant expression for supported addresses, such as a scalar global. `__has_builtin` answers 1, and a declaration of the same name hides it. | #330 |
| `__builtin_strlen(s)` | libycxx's `<ycxx/core/stdexcept.hpp>` | An unqualified direct call converts its argument to `const char*` and returns the number of characters before the first zero as the target's `size_t`. Constant evaluation checks each read against the interpreter's object and lifetime rules. Native code scans the supplied storage directly and requires readable bytes through the terminator. `__has_builtin` answers 1, and a declaration of the same name hides it. | #531 |
| `__builtin_trap()` | libycxx's `<ycxx/core/error.hpp>` | A zero-argument direct call of type `void` terminates execution. Linux x86-64 emits UD2 and Darwin arm64 emits BRK. `__has_builtin` answers 1. | #548 |

| `__builtin_constant_p` | `libkern/_OSByteOrder.h`'s `__DARWIN_OSSwapInt16/32/64` (`ntohs`, `htonl`, …) | Not yet: diagnosed as above where a program uses the macros | — |
| `__builtin_offsetof` | `sys/_types.h`'s `__offsetof`, libycxx's `offsetof` | `size_t` constant from the target record layout for a direct non-static data member of an ordinary standard-layout class or union. Diagnoses an invalid member or bit-field. | #248 |
| `__builtin_expect` | the SDK's `assert.h`'s `assert` | Not yet: diagnosed as above where a program uses `assert`, which did not compile before #229 either (its other path calls `abort` undeclared; this one also needs `__func__`, [dcl.fct.def.general], which ycxx does not have yet) | — |

The built-in functions marked "not yet" are listed in one table, `lex::lacking_builtins`
(#248). Those builtins are diagnosed as unsupported. An unrecognized `__builtin_` name follows
ordinary lookup, so a requires-expression that probes an undeclared name is unsatisfied, as
libycxx's in-language probes need (`tests/own/builtins/unknown-probe.accept.cpp`).

The other `__GNUC__` tests in those headers select nothing new for ycxx: `sys/cdefs.h`'s
`#warning "Unsupported compiler detected"` goes; `__signed` is `sys/cdefs.h`'s macro for
`signed`; `__header_inline` is `inline` in C++; `__deprecated_msg`, the availability macros and the
`GCC diagnostic` pragmas want GCC 4.5 or 4.6; `__DARWIN_NULL` wants `__GNUG__` (`__null`);
`_stdio.h`'s inline `__sputc` wants `__STDC__`; the `_FORTIFY_SOURCE` paths are C only; and
`libkern/arm/_OSByteOrder.h`'s byte swaps use `__builtin_bswap32` and `__builtin_bswap64` only
under `__llvm__` (their portable path has a local union, which ycxx does not have yet).

The standard `[[…]]` attribute syntax is available on declarations and statements. The parser
skips unrecognized attributes ([dcl.attr.grammar]/6).
